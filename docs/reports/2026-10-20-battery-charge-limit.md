# 电池充电限值（50% / 60%）—— 逆向结论与实现报告

日期：2026-10-20
机器：Lecoo N175L（Core Ultra 5 125H，AMI ALASKA BIOS `LECOO_BIOS_H143MLR100_R09`）
目标：像联想 FlexiCharger 那样，用软件把电池充电上限压到 50% / 60%

---

## 一句话结论

功能已经做进 `LecooFanGUI`（图形卡片 + 命令行 + 开机自动补写），寄存器写法和上游开源项目
`LaVashikk/Lecoo-Control-Center` **逐字节一致**；但**本机 N175L 的固件没有表现出认这个限值的行为**——
限值能写进 EC、能读回来，电池该充还是充。

**2026-10-21 修正**：第一版把结论写成「固件确定不执行」，依据里有一半是无效实验
（详见 §2.1）。现在能确定的是：阈值 60% / 40% 在电池 96~97% 时都没拦住；
还不能排除「固件只在电量低于某个水位时才认账」。**要一次结案，得把电池放到 60% 以下再充。**

另外一个附带发现：**这台机器的充电器自己就会在 ~95% 停充**，所以「电池永远显示 95%、
看不到 100%」不是故障，也不是被限住了，是充电终止阈值本来就定得早。

---

## 1. 硬件事实（已验证）

| 项 | 值 |
|---|---|
| EC | ITE IT5570-02，I/O 端口 `0x4E`（`inpoutx64.dll`） |
| EC 事务 | `87 01 55 55` 进入，索引/数据口 `0x2E`/`0x2F`，子口 `0x11`/`0x10`（地址高低）、`0x12`（数据），`02 02` 退出 |
| HRAM 基址 | `0x0400` |
| 实时电量 | EC `0x0493`（同时用 `GetSystemPowerStatus` 交叉验证） |

**FlexiCharger 两个寄存器**（与联想 FlexiCharger 同款）：

- `0x04BB` = 停充百分比（stop）
- `0x04BC` = 复充百分比（resume，比 stop 低 5%，做迟滞）

上游开源项目 N155A 配置：`min = Ram(0xBC)`、`max = Ram(0xBB)`、`full_max = 0`，
写序 = 先 `0xBC` 后 `0xBB`；「不限制」= 写 `0x00 / 0x00`。
本项目的实现（含写序、不限制时的 0/0）与它完全一致。

**另一种机制（上游给新板用的 PolicyByte）**：`Reg(0x0414)`，位含义
`ENABLE=0x01` / `POLICY=0x02` / `LATCH=0x04`，`V_FULL=0x00` / `V_PRESERVE=0x03` / `V_FREEZE=0x07`。
本机也试过，一样无效（已把 `0x0414` 恢复成 `0x00`）。

## 2. 「不生效」的证据链（2026-10-21 修正过，见 §2.1）

五组实验，全部在插电、电池 95%~97% 的状态下做的：

| # | 谁做的 | 写了什么 | 结果 | 现在怎么看 |
|---|---|---|---|---|
| 1 | 本项目 CLI `--charge 60` | `0x04BB=60` `0x04BC=55` | 回读 60/55 正常；电量 97→96 **仍在充** | **有效**（阈值远低于当时电量） |
| 2 | 厂商工具（`lecoo-ec-daemon.exe` v0.4.0，daemon 以**服务**方式常驻） | 40% | 无效，仍在充 | **有效** |
| 3 | 厂商工具 | 95% | 无效，仍在充 | **无效**（95% 正好落在充电器自己的停充点上，看不出区别） |
| 4 | 上游新机制 PolicyByte | `0x0414 = 0x03`（PRESERVE） | 回读正常，**仍在充** | 有效（阈值 61~76） |
| 5 | 当时的「决定性试验」：停充阈值 = 当前电量（95%），已过线 | `0x04BB=95` `0x04BC=90` | 盯 120 秒：EC `0x0493` 走到 96%，系统 `BatteryFlag` 始终是 `charging` | **无效**（见下） |

### 2.1 修正：第 3、5 组是无效实验

用 `powercfg /batteryreport` + ACPI `root\wmi\BatteryStatus` 复查后发现：
**这台机器的充电器自己就会在 ~95% 停充**，所以把阈值设成 95% 等于什么都没设——
第 5 组「阈值 = 当前电量」根本区分不出「限值生效了」和「充电器本来就停在这儿」。
（当时 Windows 一直报 `charging`，误导了判断；ACPI 报的是 **充电电流 0 mW**。）

### 2.2 这台机器的电池到底在什么状态

| 观测 | 值 |
|---|---|
| ACPI 电压 | 13,070 mV（设计电压 13,069 mV） |
| ACPI 充电电流 / 放电电流 | **0 mW / 0 mW**（连续 3 分钟不变） |
| ACPI 剩余电量 / 满充容量 | 53,938 mWh / 56,611 mWh = **95.3%** |
| EC 实时 SoC `0x0493` | 96（连续 20 分钟不变，EC 全量快照逐字节 diff：无任何变化） |
| Windows `BatteryFlag` | 0x09（= high + **charging**，但这是平滑过的状态位，不代表真的有电流） |
| 电量报告里的历史 | 2026-10-14 曾显示 **99%**、57,813 mWh；本轮满充容量已从 ~61,000 掉到 ~54,800 mWh（老化约 10%） |

**结论**：电池是「充满后被充电器提前终止」的状态——电流归零、电量停在 95~96%、
电量计把满充容量按 56,611 mWh 算，所以显示 95% 而不是 100%。
**这不是故障，也不是被限住了**，是充电终止阈值本来就定得早（很多笔记本都这样）。

### 2.3 现在的结论（比第一版弱，但更准确）

- **仍然成立**：阈值 60% / 40% 在电池 96~97% 时都没有让充电器停 —— 固件不是简单地
  「读一下寄存器就停充」。
- **仍未排除**：固件可能只在「电量低于某个水位」时才认这个上限（上游给 N161A 写的
  `arm_below: 60` 就是这个模式）。要排除它，**必须把电池放到 60% 以下再插上电**。
- **唯一能一次结案的实验**：电池放到 50% 左右 → 插上电 → 看它在 60% 停不停。
  这一步同时满足「低于水位」和「越过阈值」两个条件，能把上面的分支一次排掉。

| EC 访问 | 新增跨进程互斥（命名互斥体 `Local\LecooFanEcAccess` + 进程内锁），所有寄存器读写都走事务锁 |

限值档位与复充值的对应：40/35、50/40、60/55、80/70、95/90（%）。

> EC 事务锁是 2026-10-20 22:56 那次意外断电的整改：当时有三个进程同时在读写 EC。
> 见下一节。

**顺带修掉的一个坑**：GUI 启动时会先恢复 CPU/风扇档位并顺手 `SaveSettings()`，
那时 `chargeLimitStop` 还是 -1（配置还没读），直接把 `charge=-1` 写回文件，
**把上次配好的充电限值抹掉**——开机补写任务就再也认不出限值，等于白装。
现在 `SaveSettings()` 在没读到限值时保留文件里的旧值，日志行里也带上 `charge=` 方便对账。

**部署**：这台机器上用户实际跑的是 `C:\Program Files\LecooFan\LecooFanGUI.exe`（安装版），
不是仓库里的开发版。新版已覆盖安装版，两个计划任务（`LecooFan`、`LecooFanCharge`）
也重新注册成指向安装版路径。

## 4. 顺带查清的那次「关机」

2026-10-20 22:56:51 的关机**不是**任何程序发起的关机，也不是蓝屏：

- 系统事件日志里当天唯一的 Event 1074（正常关机请求）发生在 **22:34:57**，发起方是 `StartMenuExperienceHost`
- 22:56:51 只有 Kernel-Power 41（`BugcheckCode=0`、`PowerButtonTimestamp=0`、`LongPowerButtonPressDetected=false`）、
  EventLog 6008（意外断电）、Kernel-General 20，**没有 WER 崩溃报告**
- 结论：掉电式硬断电，不是被关机、不是 BSOD。时间点正好在「从待机唤醒 19 秒后」，
  而当时有三个进程在并发访问 EC

**整改**：所有 EC 读写现在都在事务锁里（跨进程命名互斥体 + 进程内 `lock`），
多个进程不会再交错写同一批寄存器。程序启动时若发现官方 `lecoo-ec-daemon` 在跑会给出提示。

## 5. 风险与注意事项

- 写 `0x04BB/0x04BC` 在本机**没有任何副作用**：回读正常，充电行为不变（因为固件不认）
- `0x0414` 实验值已恢复 `0x00`；`0x04BB/0x04BC` 当前留在 `60/55`（用户要的档位）
- EC RAM 断电即失，所以靠 `LecooFanCharge` 计划任务在每次登录时补写
- 不要在未知 EC 地址上乱写：写错寄存器有可能让充电器失控（本次断电事故就是这个量级的风险）

## 6. 下一阶段计划（待批准）

| 轨道 | 内容 | 成功判据 | 风险 |
|---|---|---|---|
| **0. 放电实验**（唯一能结案的，优先级最高） | 拔电正常用到 50% 左右 → 插上电 → 看它在 60% 停不停（`--charge status` 或 GUI 卡片实时看） | 在 60% 停 = 固件认账，功能直接可用；一路充到 95% = 固件不认，放弃软件路线 | 无。只是耗时间，机器正常使用即可 |
| **A. BIOS 电池保养模式** | 进 BIOS Setup 找「电池保养 / Battery Conservation / 充电上限」，AMI 机型通常有，通常锁 80% | 能设成 80% 就算成功（固件级，稳） | 无，只需重启进 BIOS |
| **B. 追真正的充电器开关** | 用「充电中 / 满电」两次 EC 全量快照做差分，找出随充电状态翻转的字节，再逐个试探哪个是「充电器使能」位 | 找到一个写 0 就能停充的字节 | 中——写错可能让充电器失灵，需断电复位；可先只读差分把范围缩到几个字节 |
| **C. 保持现状** | 现有实现原样交付：在 N155/N161 上是标准做法，对本机无害，且能在固件以后支持时立刻生效 | — | 无 |

B 轨道已经有一份 EC 快照（`docs/reports/snap_charging.txt`，`0x0400-0x0500`）。
不过 2026-10-21 复查发现：那份快照和 20 分钟后的另一份**逐字节完全相同**
（只有温度/风扇那几个字节在动）——说明当时电池其实已经停充，EC 里没有"充电中"的特征可差分。
要做 B 轨道，得先在**真·充电中**（比如放电到 50% 再插电）时抓一份。
