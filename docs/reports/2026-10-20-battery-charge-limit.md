# 电池充电限值（50% / 60%）—— 逆向结论与实现报告

日期：2026-10-20（2026-10-21 复查修正）
机器：Lecoo N175L（Core Ultra 5 125H，AMI ALASKA BIOS `LECOO_BIOS_H143MLR100_R09`）
目标：像联想 FlexiCharger 那样，用软件把电池充电上限压到 50% / 60%

---

## 一句话结论

功能已经做进 `LecooFanGUI`（图形卡片 + 命令行 + 开机自动补写），寄存器写法和上游开源项目
`LaVashikk/Lecoo-Control-Center` **逐字节一致**。

**但 2026-10-21 复查发现：所有「限值没生效」的实验都做在了「充电器根本没在工作」的时段，
所以一条都不能用来判断固件认不认这个限值。** 现在的事实是：

- 这台机器**曾经充电完全正常**，两天内两次充到 **100%**（10-16 09:05、10-17 04:30），
  从 66% 冲到 100% 用了 2 小时（≈24 W）——电池和充电器都是好的。
- 从 **10-19 晚上**起，插着电却**不再进电**：ACPI 真实充电电流 **0 mW**、放电电流 0 mW，
  电量从 99.6% 一路漂到 95.3%，EC 实时电量冻结在 96。
- 把充电阈值清成「不限制」（`0x04BB/0x04BC = 0/0`，上游 `full` 模式的写法）再观察 2 分钟：
  **电流仍然是 0**。所以当前这个「卡在 95%」跟我们的限值设置无关，是充电器自己没在工作。

**「为什么永远是 95%、看不到 100%」的答案**：95% 不是上限、不是被锁住，
是**充电器从 10-19 晚上起就停工了**，包在插电状态下慢慢自放电，电量计的数字跟着往下漂；
而 Windows 显示的百分比来自电量计估算，它在 95~99 之间漂，永远不会稳定停在 100。
（顺带：10-16 和 10-17 确实出现过 100%，只是那几秒没人盯着。）

**要一次结案限值这件事，前提是先把充电器救活**（拔插适配器 / 换口 / 放电唤醒），
然后把电池放到 60% 以下再插电，看它在 60% 停不停。

## 1. 硬件事实（已验证）

| 项 | 值 |
|---|---|
| EC | ITE IT5570-02，I/O 端口 `0x4E`（`inpoutx64.dll`） |
| EC 事务 | `87 01 55 55` 进入，索引/数据口 `0x2E`/`0x2F`，子口 `0x11`/`0x10`（地址高低）、`0x12`（数据），`02 02` 退出 |
| HRAM 基址 | `0x0400` |
| 实时电量 | EC `0x0493`（同时用 `GetSystemPowerStatus` 交叉验证） |
| 电池 | 4S2P，设计 60,042 mWh（满充 56,611 mWh，老化约 6%） |

**FlexiCharger 两个寄存器**（与联想 FlexiCharger 同款）：

- `0x04BB` = 停充百分比（stop）
- `0x04BC` = 复充百分比（resume，比 stop 低 5%，做迟滞）

上游开源项目 N155A 配置：`min = Ram(0xBC)`、`max = Ram(0xBB)`、`full_max = 0`，
写序 = 先 `0xBC` 后 `0xBB`；「不限制」= 写 `0x00 / 0x00`。
本项目的实现（含写序、不限制时的 0/0）与它完全一致。

**另一种机制（上游给新板用的 PolicyByte）**：`Reg(0x0414)`，位含义
`ENABLE=0x01` / `POLICY=0x02` / `LATCH=0x04`，`V_FULL=0x00` / `V_PRESERVE=0x03` / `V_FREEZE=0x07`。
本机也试过，一样无效（已把 `0x0414` 恢复成 `0x00`）。

**一个重要的落差**：上游项目和厂商 daemon 的板子表都只有 `N155A / N155C / N155D / N161A`，
**没有 N175L**（daemon 二进制里能直接看到这四个字符串）。
也就是说：我们抄的那套 FlexiCharger 寄存器语义，厂商自己都没在这台机器上支持过，
指望它在 N175L 上生效本来就不该抱太大期望。

## 2. 「限值为什么不生效」—— 这部分结论全部推翻重写

### 2.1 第一版的五组实验（2026-10-20）

| # | 谁做的 | 写了什么 | 当时的现象 | 现在怎么看 |
|---|---|---|---|---|
| 1 | 本项目 CLI `--charge 60` | `0x04BB=60` `0x04BC=55` | 回读 60/55 正常；电量 97→96「仍在充」 | **无效** |
| 2 | 厂商工具（daemon v0.4.0，服务方式常驻） | 40% | 「仍在充」 | **无效** |
| 3 | 厂商工具 | 95% | 「仍在充」 | **无效** |
| 4 | 上游新机制 PolicyByte | `0x0414 = 0x03` | 回读正常，「仍在充」 | **无效** |
| 5 | 当时的「决定性试验」：阈值 = 当前电量 95% | `0x04BB=95` `0x04BC=90` | 盯 120 秒，EC 0x0493 走到 96% | **无效** |

**为什么五组全作废**：当时判定「还在充」用的是 Windows 的 `BatteryFlag` 充电位，
而那个位是**平滑过的状态位，插着电就恒为真**；真正可信的 ACPI 电流当时就是 **0 mW**。
换句话说，五次实验里电池**一次都没在充**，所以「限值设了 60% 之后还在充」这句话本身
就是观察错误 —— 没有电流可观察。

### 2.2 电池历史：这台机器充电一直很正常（`powercfg /batteryreport`）

| 时间 | 状态 | 电量 |
|---|---|---|
| 10-15 16:25 → 16:58 | 插电 | 62%（36,060 mWh）→ **85%**（49,539 mWh），33 分钟 +13,479 mWh ≈ **24.5 W** |
| 10-15 17:21 → 17:34 | 插电 | 81% → 89% |
| 10-16 09:05 | 插电 | **100%**（56,622 mWh） |
| 10-17 02:27 → 04:30 | 插电 | 66%（37,192）→ **100%**（56,506），2 小时 +19,314 mWh ≈ **24 W** |

所以：**充电能力正常、100% 到得了、限值 60/80/90 也没拦住过任何一次**。

### 2.3 从 10-19 晚上起，插着电却不再进电

| 时间 | 电源 | 电量（mWh） |
|---|---|---|
| 10-19 14:52 → 18:41 | AC | 55,700 → 55,770（涓流补电 +70） |
| 10-19 19:11 → 21:44 | AC | 55,759 → **55,024**（开始往下掉） |
| 10-19 21:23 | AC | 55,700 → 55,047（插拔瞬间掉 653 mWh） |
| 10-20 全天 | AC | 54,860 → 54,697（持续缓慢下滑） |
| 10-20 23:43 → 23:47 | AC | 54,685 → **53,938**（又掉 747 mWh） |
| 现在（10-21 00:30） | AC | 53,938（**95.3%**），ACPI 电流 0 mW |

**当前实时状态**：

| 观测 | 值 |
|---|---|
| ACPI 充电电流 / 放电电流 | **0 mW / 0 mW**（连读 2 分钟不变） |
| ACPI `Charging` 布尔位 | True（只表示「适配器在位、允许充电」，不代表有电流） |
| ACPI 剩余 / 满充 | 53,938 / 56,611 mWh = **95.3%** |
| EC 实时 SoC `0x0493` | 96（冻结） |
| Windows `BatteryFlag` | 0x09（= high + charging，**插电即恒真，不可作证据**） |
| ACPI 电压 | 13,071 mV —— 对 4S2P 电池（满充约 16.8 V）是矛盾的，属于 EC 上报的脏数据，不作依据 |

### 2.4 决定性实验：把限值清掉，电流依然是 0

- 停掉 GUI（否则它每几秒就把限值补写回去 —— 实测我写 `0/0` 后 15 秒就被改回 `60/55`）
- 写 `0x04BC=0`、`0x04BB=0`（上游 `full` 模式 = 不限制），回读确认
- 观察 120 秒，每 15 秒采样

```
t+0s    soc=96  0x4BB=0  0x4BC=0   rate=0 dRate=0   rem=53938
t+60s   soc=96  0x4BB=0  0x4BC=0   rate=0 dRate=0   rem=53938
t+120s  soc=96  0x4BB=0  0x4BC=0   rate=0 dRate=0   rem=53938
```

**结论：当前这个「95% 不动」不是限值挡住的。** 清掉限值，充电器照样 0 mW。

### 2.5 现在的判断

1. 「95%」**不是**上限、**不是**被锁、**不是**我们的功能造成的 —— 充电器从 10-19 晚上起就没在工作。
2. 「固件不认限值」这句话**仍然没有证据**（因为从来就没在充电的时候测过）；但反过来，
   也没证据说固件认。**这个问题现在是悬空的，不是已知的。**
3. 要同时解决两件事：**先把充电器救活**（否则限值无从谈起），**再在真充电状态下跌到 60% 以下测阈值**。

### 2.6 充电器为什么停工？四个候选

| 候选 | 说明 | 怎么验 |
|---|---|---|
| **A. 适配器/接口** | 适配器没真正供电，或 USB-C 口接触/协商异常，但 EC 仍认为「适配器在位」 | **拔下来等 10 秒再插上**（换另一个口更好），看 ACPI 电流是否变正 —— 30 秒的事，最该先试 |
| **B. 电池 BMS 保护/休眠** | 长期满电存放后 BMS 进入深度休眠，醒着但拒绝充电；放电唤醒是标准解法 | 正常用到 50% 再插电（本来就要做的放电实验，一起做） |
| **C. 固件/EC 锁死充电器使能位** | EC 里有个「充电器使能」位被置 0 了 | 需要一份**真·充电中**的 EC 快照，和一份停充快照差分（见 §6 B 轨道） |
| **D. 电池老化抬高了充电终止点** | 老化后充电更早终止 | **不支持**：10-17 同一块电池冲到 100%，老化不会三天突变 |

> EC 事务锁是 2026-10-20 22:56 那次意外断电的整改：当时有三个进程同时在读写 EC。
> 见 §4。

**顺带修掉的一个坑**：GUI 启动时会先恢复 CPU/风扇档位并顺手 `SaveSettings()`，
那时 `chargeLimitStop` 还是 -1（配置还没读），直接把 `charge=-1` 写回文件，
**把上次配好的充电限值抹掉**——开机补写任务就再也认不出限值，等于白装。
现在 `SaveSettings()` 在没读到限值时保留文件里的旧值，日志行里也带上 `charge=` 方便对账。

**部署**：这台机器上用户实际跑的是 `C:\Program Files\LecooFan\LecooFanGUI.exe`（安装版），
不是仓库里的开发版。新版已覆盖安装版，两个计划任务（`LecooFan`、`LecooFanCharge`）
也重新注册成指向安装版路径。

## 4. 顺带查清的那次「关机」

2026-10-20 22:56:51 的关机**不是**任何程序发起的关机，也不是蓝屏：

- 系统事件日志里当天唯一的 Event 1074（正常关机请求）发生在 **22:34:57**，发起方是 `StartMenuExperienceHost`
- 22:56:51 只有 Kernel-Power 41（`BugcheckCode=0`、`PowerButtonTimestamp=0`、`LongPowerButtonPressDetected=false`）、
  EventLog 6008（意外断电）、Kernel-General 20，**没有 WER 崩溃报告**
- 结论：掉电式硬断电，不是被关机、不是 BSOD。时间点正好在「从待机唤醒 19 秒后」，
  而当时有三个进程在并发访问 EC

**整改**：所有 EC 读写现在都在事务锁里（跨进程命名互斥体 + 进程内 `lock`），
多个进程不会再交错写同一批寄存器。程序启动时若发现官方 `lecoo-ec-daemon` 在跑会给出提示。

## 5. 风险与注意事项

- 写 `0x04BB/0x04BC` 在本机**没有任何副作用**：回读正常，充电行为不变（实测清成 0/0 也一样）
- `0x0414` 实验值已恢复 `0x00`；`0x04BB/0x04BC` 当前留在 `60/55`（用户要的档位）
- EC RAM 断电即失，所以靠 `LecooFanCharge` 计划任务在每次登录时补写
- 不要在未知 EC 地址上乱写：写错寄存器有可能让充电器失控（本次断电事故就是这个量级的风险）
- **注意 GUI 的「自动补写」行为**：它每几秒就把限值补写回 EC。做实验前要先停掉 GUI，
  否则你写的值会被它改回去（本次实测：我写 0/0，15 秒后变回 60/55）

## 6. 下一阶段计划（待批准）

| 轨道 | 内容 | 成功判据 | 风险 |
|---|---|---|---|
| **0. 救活充电器**（先做，最便宜） | 拔下适配器等 10 秒再插上；或换另一个 USB-C 口；同时用 `tools/charge_watch.py` 看 ACPI 电流 | 电流变正（几十~几百 mW 以上）= 充电器醒了 | 无 |
| **1. 放电 + 阈值结案实验** | 正常用到 50% 左右 → 插电 → 看它在 60% 停不停 | 在 60% 停 = 固件认账，功能直接可用；一路充到 95% = 固件不认，软件路线作废 | 无，只是耗时间 |
| **A. BIOS 电池保养模式** | 进 BIOS Setup 找「电池保养 / Battery Conservation / 充电上限」，AMI 机型通常有，通常锁 80% | 能设成 80% 就算成功（固件级，稳） | 无，只需重启进 BIOS |
| **B. 追真正的充电器使能位** | 等轨道 0/1 让机器真的在充电时，抓一份「真·充电中」的 EC 全量快照，和 `snap_terminated.txt` 差分，逐个试探哪个是使能位 | 找到一个写 0 就能停充的字节 | 中——写错可能让充电器失灵，需断电复位；可先只读差分把范围缩到几个字节 |
| **C. 保持现状** | 现有实现原样交付：在 N155/N161 上是标准做法，对本机无害，且能在固件以后支持时立刻生效 | — | 无 |

**为什么 B 轨道还没法做**：已有的 `snap_charging.txt`（10-20 抓的）和 `snap_terminated.txt`（今天抓的）
差分只有 9 个字节，全是温度/风扇 —— 因为**那两次抓的时候电池都没在充**，没有特征可差分。
必须等机器真的在充电时再抓。

## 附：排查工具

- `tools/charge_watch.py` —— **主力工具**：每 2 秒打一行「ACPI 真实充/放电电流 + EC 实时电量 + 阈值」，
  拔插适配器时开着它，立刻能看出充电器有没有醒
- `tools/tools_batt_watch.py` —— Windows `GetSystemPowerStatus` 轮询（只看标志位，可靠性低）
- `tools/tools_ec_read.py` / `tools_ec_write.py` / `tools_ec_snap.py` —— EC 读/写/快照
- `tools/ec_lock.py` —— 跨进程 EC 互斥（和 GUI 用的是同一个命名互斥体 `Local\LecooFanEcAccess`），
  上面三个工具现在都会先抢锁再访问，不会和 GUI 的事务撞车
- `powercfg /batteryreport /output docs/reports/battery_report.html` —— 容量历史、满充容量、老化程度
- `Get-CimInstance -Namespace root\wmi -ClassName BatteryStatus` —— **真实**充/放电电流（mW）和电压
  （Windows 自己的 `BatteryFlag` 是平滑过的状态位，插电时永远报 "charging"，别拿它当证据）
- `tools/upstream/` —— 从上游仓库拉的 `boards.rs` / `flexicharger.rs` 原文（对照用）
